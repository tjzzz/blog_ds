# 实验流量分层与正交设计

> 目标：如果要设计一个线上抽样/分流平台，能支撑多个业务、多个实验长期并行运行，同时保证随机、互斥、正交、可追踪、可回滚。

## 1. 平台要解决的问题

线上实验流量平台本质上是一个「稳定分桶 + 流量治理 + 配置下发 + 命中记录」系统。

它要解决：

- 同一个用户每次访问都能稳定命中同一个实验版本；
- 多个实验可以并行，不互相污染；
- 需要互斥的实验不能同时作用到同一用户；
- 不需要互斥的实验可以正交运行，提高流量复用率；
- 可以按人群、场景、端、地域、版本、时间进行圈选；
- 实验上线后，能追踪用户命中了哪个实验、哪个版本、哪个参数；
- 支持小流量、灰度、扩量、暂停、回滚、全量。

## 2. 核心抽象：域、层、桶、实验、版本

| 抽象 | 含义 | 业务例子 |
|---|---|---|
| 实验域 Domain | 一类相对独立的业务流量空间 | 首页、搜索、推荐、交易、营销、履约 |
| 流量层 Layer | 域内的一层完整流量；不同层之间可正交 | 搜索排序层、UI 样式层、广告策略层 |
| 桶 Bucket | 将一层流量切成固定份数后的最小分配单位 | 1000 个桶，每桶约 0.1% 用户 |
| 实验 Experiment | 占用某些桶的策略验证单元 | 搜索召回策略实验、下单页文案实验 |
| 版本 Variant | 对照组/实验组/多实验组 | control、treatment_1、treatment_2 |

一个常见设计：

```text
用户请求
  → 识别实验域：search / feed / order / marketing
  → 判断用户是否满足受众条件
  → 在该域下进入多个流量层
  → 每一层独立 hash 分桶
  → 命中该层上占用桶位的实验
  → 在实验内再次分配到 control / treatment
  → 返回实验参数 + 记录曝光日志
```

## 3. 分桶机制怎么设计

### 3.1 分桶键

优先使用稳定用户级 ID：

- 登录用户：user_id
- 未登录用户：device_id / cookie_id
- B 端业务：shop_id / merchant_id / seller_id
- 内容/商品策略：item_id 不是默认实验单元，除非实验目标是内容/商品维度

分桶键要跟「实验单元」一致。比如用户体验实验按 user_id 分桶；商家补贴策略按 merchant_id 分桶；订单履约策略可能要按 order_id 或 user_id 结合业务判断。

### 3.2 Hash 分桶

常见方式：

```text
bucket = hash(layer_id + experiment_salt + unit_id) % bucket_num
```

设计要点：

- `layer_id` 保证不同层之间重新随机，形成正交；
- `experiment_salt` 防止不同实验复用同一随机序列；
- `unit_id` 保证同一实验单元稳定命中；
- `bucket_num` 建议足够细，如 1000、10000，方便小流量扩量。

## 4. 正交和互斥怎么落到平台

| 关系 | 平台实现 | 适用场景 |
|---|---|---|
| 同层互斥 | 一个 Layer 内，桶只能被一个实验占用 | 两个搜索排序实验、两个价格策略实验，不能同时影响同一指标 |
| 跨层正交 | 用户进入每层时重新 hash，不同层实验近似独立 | UI 实验和推荐策略实验同时运行，希望复用流量 |
| 父子实验 | 子实验只在父实验某个版本流量内运行 | 黑白盒实验、Holdout、策略包内部再迭代 |
| 隔离域 | 某类实验独占一个业务域或人群 | 高风险策略、核心交易链路、长期 holdout |

业务上判断是否互斥：

- 会不会同时改变同一个用户体验？
- 会不会共同影响同一个核心指标，导致归因不清？
- 一个实验结果是否依赖另一个实验版本？
- 是否存在工程依赖或策略依赖？

如果答案是「会」，优先同层互斥；如果只是弱相关，可以跨层正交并在分析中做交互检查。

## 5. 线上抽样平台的模块设计

| 模块 | 关键能力 | 设计要点 |
|---|---|---|
| 实验配置中心 | 创建实验、配置版本、分配流量 | 配置必须版本化，支持审批和回滚 |
| 分流引擎 | 实时判断用户命中哪个实验版本 | 高并发、低延迟、稳定 hash、容灾降级 |
| 受众圈选 | 按用户属性、行为、端、地域、版本过滤 | 圈选条件必须在 control/treatment 都可观测，避免触发偏差 |
| 流量层管理 | 管理域、层、桶、占用关系 | 可视化展示冲突、剩余流量、互斥关系 |
| 参数下发 | 返回实验参数/策略开关 | 参数要有默认值；失败时回退到 control |
| 曝光日志 | 记录用户实际命中和曝光 | 分析必须基于实际曝光/触发，而不是只看配置 |
| 监控告警 | 检查流量、指标、数据质量 | SRM、分桶均匀性、流量异常、错误率、护栏指标 |
| 分析报表 | 输出实验效果 | 指标值、涨跌幅、p-value、置信区间、分层分析 |

| 表 | 关键字段 |

| experiment_decision | experiment_id、decision、reason、risk、operator、decision_time |

## 7. 平台必须内置的质量检查

上线前：

- 实验是否选择了正确实验域和流量层；
- 同层是否存在流量冲突；
- 受众条件是否会导致实验组/对照组不可比；
- 指标口径和数据集是否已确认；
- control 默认参数是否可回退。

运行中：

- 流量是否按配置比例进入；
- 是否出现 SRM；
- 各版本错误率、延迟、崩溃率是否异常；
- 曝光日志和业务日志是否能 join 上；
- 关键护栏指标是否异常。

分析前：

- 先看 SRM 和数据完整性；
- 再看核心指标；
- 最后看分层、长期效果和业务解释。

## 8. 一个业务化的设计模板

如果让我设计「搜索实验分流平台」：

```text
Domain: Search
Layer 1: 召回层实验，互斥搜索召回相关策略
Layer 2: 粗排/精排层实验，互斥排序模型相关策略
Layer 3: UI 展示层实验，互斥卡片样式、摘要、按钮等 UI 实验
Layer 4: 贯穿层 / Holdout 层，用于长期保留基线流量
```

- 排序模型 A/B 和另一个排序模型实验：同层互斥；
- 排序模型实验和搜索结果页 UI 实验：可跨层正交；
- 多个算法策略都要合并上线时：可以打包到贯穿层做长期验证；
- 对全量上线策略：保留小流量反转/holdout，观察长期效果。
