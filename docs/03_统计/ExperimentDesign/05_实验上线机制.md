实验上线机制把实验从“一次性验证”变成“低风险迭代链路”。它关注的不只是统计显著，而是如何安全上线、逐步放量、分析决策、全量发布和复盘沉淀。

一句话：**先验证链路，再验证安全，再验证效果，最后做上线决策和复盘**。

## 1. 标准上线链路

一个策略 / 功能从 idea 到全量，推荐经历：

```text
离线验证
  → A/A 或空转检查
  → 小流量 AB
  → 灰度扩量
  → 稳定性观察
  → 数据回收与实验分析
  → 全量发布或回滚
  → 反转 / holdout 长期观察
  → 复盘沉淀
```

不是所有实验都必须完整走完，但高风险、核心链路、算法策略、长期收益不确定的实验，应尽量走完整链路。

## 2. 实验状态机

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 草稿 | 实验方案未评审 | 评审通过 / 驳回 |
| 待上线 | 配置完成，等待发布窗口 | 上线 / 取消 |
| A/A 空转 | 分流已开，但各组策略一致 | 分桶和指标无异常 |
| 小流量实验 | 低比例真实流量进入 | 护栏无异常且链路稳定 |
| 灰度扩量 | 逐步提高实验流量 | 效果稳定进入全量；异常回滚 |
| 数据回收 | 停止新流量，等待转化窗口结束 | 指标窗口完整 |
| 分析决策 | 指标计算完成 | 上线 / 回滚 / 继续实验 / 重做 |
| 全量发布 | 实验策略成为默认策略 | 进入反转或长期监控 |
| 反转观察 | 小流量继续保留旧策略对照 | 长期指标稳定后结束 |
| 归档复盘 | 决策完成 | 形成案例库和方法论 |

## 3. A/A 或空转

A/A 或空转的目标不是验证策略收益，而是验证实验系统本身是否可信。

检查重点：

- 分组比例是否符合配置；
- 是否出现 SRM；
- 曝光日志是否准确；
- 业务日志和曝光日志是否能 join；
- 指标计算是否能稳定产出；
- 对照组和“实验组”在无策略差异时是否无系统性差异。

## 4. 小流量实验

小流量不是为了直接证明最终收益，而是为了降低风险、发现明显问题。

适合小流量先行：

- 新功能影响核心路径；
- 推荐 / 搜索 / 广告模型改动；
- 交易、支付、履约等强风险链路；
- 埋点或指标链路未完全稳定；
- 预期收益大但风险也大。

小流量阶段重点看：

- 错误率、崩溃率、延迟、投诉、退款等护栏指标；
- 曝光、点击、转化链路是否完整；
- 分流比例是否符合预期；
- 是否出现明显负向。

不要在样本量不足的小流量阶段过度解读 p-value。

## 5. 灰度扩量

推荐扩量节奏：

| 阶段 | 流量比例 | 判断重点 |
|---|---|---|
| 冒烟验证 | 0.5% - 1% | 工程稳定性、日志、埋点、配置是否正确 |
| 小流量 | 5% | 护栏指标、SRM、核心链路是否异常 |
| 中流量 | 10% - 20% | 核心指标方向、分层表现、负反馈 |
| 大流量 | 50% | 指标显著性、稳定性、资源成本 |
| 全量 | 100% | 上线后长期监控、反转 / holdout |

每次扩量前必须检查：

- 上一阶段是否跑满最低观察窗口；
- 护栏指标是否无显著负向；
- 核心指标方向是否稳定；
- 数据质量是否通过；
- 是否有活动、节假日、版本发布等干扰。

## 6. 实验分析前的数据质量检查

实验分析之前，先问数据能不能信。

| 检查项 | 说明 |
|---|---|
| SRM | 实际分组比例是否明显偏离配置 |
| 曝光完整性 | 实验命中和曝光日志是否完整 |
| 指标完整性 | 核心指标、护栏指标是否能产出 |
| Join 质量 | 曝光、行为、订单、用户表是否能正确关联 |
| 异常流量 | 内部用户、机器人、黑产、异常峰值是否处理 |
| 时间窗口 | 是否覆盖完整业务周期和归因窗口 |
| 版本干扰 | 是否有并行发布、活动、节假日、其他实验影响 |

数据质量异常时，不要直接做上线决策。

## 7. 决策规则

| 结果 | 建议动作 |
|---|---|
| 核心指标显著正向，护栏无负向 | 扩量 / 全量 / 进入反转观察 |
| 核心指标正向但不显著 | 延长周期、扩大样本、检查方差、评估业务价值 |
| 核心指标持平，护栏无异常 | 成本低可放弃；战略重要可重构实验 |
| 核心指标负向或护栏负向 | 暂停 / 回滚 / 定位原因 |
| SRM 或数据质量异常 | 不做上线决策，先修数据和分流问题 |
| 分层结果冲突 | 检查辛普森悖论、样本偏差、异质性效果 |

## 8. 反转实验与 Holdout

反转实验用于验证：短期 AB 正向后，全量上线是否仍有长期收益，是否存在新奇效应或长期负面影响。

典型做法：

```text
原实验：A=旧策略，B=新策略，B 胜出
全量：新策略成为默认策略
反转：从原 A 组或保留流量中抽小部分继续使用旧策略
对比：新默认策略 vs 旧策略小流量对照
```

适用场景：

- 算法模型改版；
- 推荐 / 搜索排序策略；
- 影响用户长期习惯的产品功能；
- 短期指标正向、长期指标不确定；
- 需要长期确认大盘收益。

不建议反转的情况：

- 原实验已经显著负向；
- 新策略涉及强合规、安全修复，不能让用户继续使用旧策略；
- 原策略不可再现，或工程上已经删除；
- 对照用户体验损伤过大；
- 反转本身会引入明显伦理、合规或业务风险。

## 9. 打包验证

当多个小策略单独收益很小，或策略之间有交互时，可以做打包验证。

```text
Base：线上旧策略包
Package：多个待上线策略组成的新策略包
在贯穿层 / holdout 层做长期 AB
观察大盘核心指标、护栏指标、长期留存 / 转化
```

注意：

- 打包验证回答“整体是否有效”，不能精确拆分每个策略贡献；
- 打包正向后，要记录包内策略清单；
- 打包负向时，需要拆包回溯拖累策略。

## 10. 平台要支持的迭代能力

为了支撑真实业务里的实验迭代，实验平台不能只支持“开一个 AB”，还要支持完整生命周期管理：

| 能力 | 说明 |
|---|---|
| 实验状态机 | 草稿、待上线、运行中、暂停、数据回收、报告完成、归档 |
| 动态调流 | 支持扩量、缩量、暂停、恢复 |
| 灰度配置 | 支持按人群、端、版本、地域、白名单发布 |
| 一键回滚 | 配置快速回退到 control / default |
| 反转实验 | 从原对照组或保留桶继续抽样观察长期效果 |
| 父子实验 | 支持 holdout、黑白盒、策略包内部再迭代 |
| 打包验证 | 支持多个策略组成 package 做整体效果评估 |
| 决策记录 | 上线、回滚、继续实验必须留痕 |
| 实验复盘 | 成功、失败、异常都进入案例库 |

## 11. 复盘沉淀

每个实验都应该沉淀：

- 实验背景和假设；
- 实验设计和流量配置；
- 指标结果和统计结论；
- 决策依据；
- 上线或回滚后的观察；
- 失败、异常、争议原因；
- 对实验平台、指标口径、业务策略的改进建议。
