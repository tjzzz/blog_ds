# 高阶实验难题：SRM 样本比例不匹配

> 核心判断：只要出现 SRM，优先怀疑分流、曝光、埋点或数据链路问题，不要直接解读实验效果。

## 1. 业务场景

SRM（Sample Ratio Mismatch）指实验实际进入各组的样本比例与预设比例不一致。

例如配置 A/B = 50%/50%，但实际曝光日志中 A=47%，B=53%。这时即使核心指标显著，也不能直接认为实验有效，因为实验组和对照组可能已经不再随机可比。

## 2. 高频原因

| 原因 | 业务例子 |
|---|---|
| 分流代码错误 | 某些端没有接入新分流逻辑，导致只进入 A 组 |
| 受众过滤不一致 | B 组策略触发后才记录曝光，A 组没有同等记录 |
| 埋点漏报 | 新版本客户端 B 组曝光埋点丢失 |
| 配置变更 | 实验运行中改过流量比例，但分析时没有按阶段拆分 |
| 用户 ID 不稳定 | 未登录用户 cookie 变化，导致重复入组或掉组 |
| 日志 join 丢失 | 只在某些请求链路能关联到 experiment_id |
| 触发式实验处理错误 | 只统计触发策略的人，但 A/B 触发概率不同 |

## 3. 识别方法

- 每个实验必须先做 SRM 检查，再看指标；
- 对实验整体、分端、分版本、分渠道、分日期分别检查；
- 对曝光日志、触发日志、指标宽表分别检查；
- 如果某个分层 SRM 明显，优先定位该分层链路问题。

判断逻辑：

```text
预期比例：50% / 50%
实际样本：A_n / B_n
做卡方检验或比例检验
如果 p-value 极小 → 认为存在 SRM 风险
```

## 4. 处理策略

| 场景 | 处理 |
|---|---|
| 分流错误 | 实验作废，修复后重跑 |
| 埋点漏报 | 不直接分析；如果能补数，补数后重新检查 SRM |
| 中途调流 | 按调流时间切分阶段，分别分析 |
| 某端异常 | 剔除异常端或单独报告，不混入整体结论 |
| 触发偏差 | 改用 intent-to-treat 或重新定义触发口径 |

原则：SRM 不是一个可以「统计修正一下就继续用」的小问题，它通常意味着随机化或数据链路坏了。

## 5. 平台化拦截

实验平台应内置：

- 上线前 A/A 测试；
- 实时 SRM 告警；
- 分端/分版本/分渠道 SRM 看板；
- 曝光日志与配置比例对账；
- 调流历史记录；
- 分析报告强制展示 SRM 检查结果。
