# 流量域设计与分流

> 父级入口：[实验设计与AB测试](../index.md)

## 定位

这个子 topic 负责回答：用户、设备、请求、商家、内容等实验单元如何进入实验，多个实验如何共享流量且不互相污染。

## 核心问题

- 实验单元应该选用户、设备、请求、门店、内容，还是更高层级的 cluster？
- 流量域如何拆分：全局层、业务层、策略层、灰度层、白名单层？
- 多个实验之间是互斥、正交、嵌套还是依赖关系？
- 如何检查分流质量，例如 SRM、样本均衡、曝光一致性和跨组污染？

## 流量域设计框架

| 设计对象 | 决策点 | 常见选择 | 检查点 |
|---|---|---|---|
| 实验单元 | 谁被随机化？ | user_id、device_id、request_id、seller_id、store_id、content_id | 单元是否稳定、是否与指标口径一致 |
| 目标人群 | 谁能进入实验？ | 新用户、活跃用户、特定城市/渠道/业务线 | 圈选条件是否导致选择偏差 |
| 分桶机制 | 如何稳定随机？ | hash 分桶、bucket、salt、版本隔离 | 同一单元是否跨组、比例是否准确 |
| 流量层 | 多实验如何共存？ | 全局层、业务域、策略域、灰度层 | 是否有互斥/正交定义 |
| 曝光归因 | 什么时候算进入实验？ | 分桶即进入、曝光才进入、触发后进入 | 是否有触发偏差、幸存者偏差 |
| 质量校验 | 分流是否正常？ | SRM、基线均衡、埋点对账 | 异常是否阻断分析 |

## 互斥 / 正交 / 嵌套的判断

- **互斥**：两个实验可能改动同一机制、同一页面、同一策略链路，互相影响结论。
- **正交**：实验影响路径相对独立，可以共享用户流量，但仍要检查交互项或护栏指标。
- **嵌套**：子实验只在某个父实验版本或人群内运行，结论边界必须写清楚。
- **依赖**：B 实验依赖 A 的上线版本或分群结果，需先确定基准版本。

## 上线前检查清单

- [ ] 实验单元与核心指标分母一致。
- [ ] 分桶键稳定且不会随登录态、设备切换、渠道切换而漂移。
- [ ] 互斥/正交流量关系已登记。
- [ ] 小流量阶段已检查 SRM、曝光量、关键埋点、核心漏斗。
- [ ] 触发型实验已明确「全量样本」和「触发样本」两套口径。
- [ ] 存在网络效应时，已考虑 cluster randomization、地理分区或准实验替代方案。
