    实验生命周期与上线治理#

    一次实验不是“开流量、看 p 值”这么简单，而是一条可追溯的决策链：问题和可行性 → 方案预注册 → 工程与数据校验 → 受控运行 → 结果分析 → 上线/回滚 → 长期观察和复盘。每一步都应有进入条件、检查项和责任人。

    生命周期一览#

    阶段 核心问题 主要产出 / 退出条件
    立项与可行性 问题是否值得验证？能否随机、观测和控制风险？ 假设、目标人群、实验可行性结论；必要时选择非随机替代评估
    方案评审 对谁、给什么处理、测什么、何时分析？ 实验单元、版本、人群、指标、样本量/周期、查看与停止规则、护栏、分析计划
    工程校验 配置、分流、埋点和指标链路是否正确？ A/A 或空转、日志 join、样本比例、回滚能力等检查结果
    小流量运行 是否有明显安全、稳定性或数据问题？ 先看护栏和链路；通过后再按方案扩量。小样本方向不当作效果结论
    正式实验 效果证据是否达到预设判断标准？ 按预设终点或序贯规则运行，保留查看、变更、异常记录
    数据成熟与决策 观察窗口完整吗？效果和风险是否支持行动？ 效应量、不确定性、护栏、业务价值及适用边界；决定上线、继续、回滚或暂缓
    上线后观察与复盘 全量环境是否与实验环境一致？长期效果如何？ 监控/holdout 方案、实现核验、决策记录和复盘改进项

    上线状态与控制点#

    方案草稿 → 评审通过 → 待上线 → 工程/A-A校验 → 小流量 → 正式实验
         → 数据成熟 → 分析决策 → 全量/回滚/继续验证 → 观察与归档

    状态名称可按平台调整，关键是不要把**技术发布状态**和**统计分析状态**混成一件事。例如停止分配新流量后，仍可能需要等待转化归因窗口成熟；全量发布也不意味着已完成长期效果验证。

    A/A、空转与冒烟#

    A/A（两组都执行同一方案）或空转主要校验实验系统，不验证新策略效果。按风险和平台成熟度选择是否开展，关注：

    • 分流配置、分配稳定性与样本比例异常（SRM）；
    • 曝光、触发、行为和转化日志完整性及关联质量；
    • 指标定义、去重、时间窗口和报表计算是否一致；
    • 实验开关、默认值和回滚路径是否可用。

    小流量、灰度扩量与正式分析#

    小流量阶段用于验证配置、服务稳定性、明显风险和埋点；它通常不足以支持最终效果判断。扩量节奏不应使用固定比例模板替代风险评估，按技术风险、指标成熟时间、流量规模和预设护栏逐阶段推进。每次扩量前确认：上一阶段数据成熟、日志与 SRM 检查通过、护栏安全、版本/人群配置正确。

    正式效果分析遵循已批准的计划。固定终点设计中，中途的效果数据不能因为普通 p 值显著就触发提前胜出；若允许依据中期证据停止，需事先采用适配的序贯规则。详见[[../统计判断与决策/序贯分析]]。

    结果处置#

    结果/事件 处理原则
    数据或分流异常 暂停解释效果，先查 SRM、埋点、窗口和版本；修复后按预设方案决定恢复或重启
    护栏触发风险阈值 按预设安全规则暂停或回滚；这不是自动的“主要指标胜负”结论
    核心效果证据正向、业务价值可接受且护栏稳定 按风险分阶段放量，并持续监控实现与长期结果
    证据不确定 按方案继续或结束并报告不确定性；不要把“不显著”解释为“无效”
    核心效果负向或不可接受 停止扩量/回滚，确认实现一致并记录原因

    决策应同时考虑效应大小、不确定性、业务价值、护栏、实施成本与适用人群，不能把“统计显著”单独当作上线按钮。具体解释框架见[[../统计判断与决策/判断方法与上线决策]]。

    长期验证：Holdout、反转与策略包#

    • Holdout：长期保留一部分对照流量，用于监测全量后的长期增量；注意代表性、污染和长期成本。
    • 反转/长期对照：在风险和伦理允许时继续保留可比较的旧策略对照，以检查新奇效应、学习效应或长期衰减。不能让用户继续承受明确有害或不合规的旧方案。
    • 策略包（bundle）验证：整体评估多个策略一起上线是否有增益；它不能单独识别包内每个策略的贡献，需留好版本清单，必要时再拆解验证。

    复盘最小记录#

    保留业务问题与假设、方案版本、随机化单位和人群、指标定义与分析窗口、样本量/停止规则、运行异常和变更、效果与不确定性、护栏、最终决策、上线后观察，以及下一步责任人。成功、失败、无结论和异常实验都应可检索。

    来源与适用范围#

    本页将生命周期阶段组织成一套便于评审和落地的工作流，不是所有团队必须照抄的唯一状态机。在线实验生命周期研究讨论了从构想到长期影响的持续迭代；Microsoft ExP 论文则从平台架构角度说明实验执行、日志处理和分析等组件如何协同。具体阶段名称和门槛应按业务风险、平台能力与法规要求设定。
