    分流与平台#

    返回 [[Z_Project_DS/topics/实验设计与AB测试/index.md|实验设计与 A/B 测试]]。

    定位：本页是后续逐题完善的知识地图，不是某家厂商产品说明，也不是直接套用的工程设计。范围从“谁有资格进实验”到“策略实际交付并留下可审计证据”，再到“多实验共享流量、长期 holdout 与发布治理”。统计推断、指标体系的详细方法仍由相邻专题维护。

    一、先看全链路：平台不只是 Hash 分桶#

    业务问题 / 目标人群 / 实验单元
          ↓
受众与身份层 ──→ 流量域/namespace ──→ 流量层/互斥池 ──→ 实验占量 ──→ 版本分配
                      ↑                       ↑                    ↓
                holdout/隔离门槛          并行冲突与容量           参数下发 / 实际曝光
                                                                    ↓
                    assignment → delivery → exposure → outcome → 质量告警与分析
                                          ↑
                            配置版本、灰度、回滚、审计贯穿全程

    可以把平台分为三张“平面”：**控制面**管配置、审批、流量容量与生命周期；**服务面**在真实请求中完成身份识别、路由、稳定分配和参数下发；**证据面**记录分配、实际交付、曝光和结果，并对异常报警。这是本文的组织框架，而非某一厂商的固定术语。

    Google 的经典重叠实验架构将 domain 用作流量分段、layer 用作可同时运行的参数子集；同层实验争用/隔离流量，跨层可以重叠。Statsig、LaunchDarkly 也用 layer/universe 管理互斥实验，但各家对 holdout 与 layer 的组合限制不同。因此**不要把“域、层、桶、holdout”的某一种产品实现当作通用标准**；以下按它们要解决的问题组织，而不是按界面名词组织。Google 原始论文 · Statsig Layers 文档 · LaunchDarkly Layers 文档

    二、模块地图：十个问题、十个专题#

    模块 核心问题 未来专题应回答的关键点 当前库内基础
    1. 科学性与准入 分流结果凭什么可信？ 目标人群与入组人群、随机化单位、分流均匀性/SRM、基线可比、代表性、A/A 与假阳性校准 [[01_分流科学性与平台校验.md
    2. 对象、身份与受众 谁是同一个实验对象，谁有资格进入？ user/device/account/cluster 等单位；匿名转登录与跨端合并；处理前圈选；身份漂移、重复入组、机器人过滤 平台旧稿有 key 对比；身份图谱与圈选顺序待建
    3. 分桶与分配引擎 如何稳定、可复现地把单元分到实验和版本？ Hash/salt、桶空间、两级分配（先实验占量、再版本比例）、配置变更、扩缩量时的重洗与粘滞性 [[ExperimentDesign__03_抽样平台_流量分组.md
    4. 流量域与流量层 多实验如何共享、隔离并利用流量？ domain/namespace 的受众边界；layer 的互斥池；跨层重叠；层容量、空桶、饥饿；同参数冲突与交互效应 [[02_流量域设计与分流.md
    5. 处理交付与曝光 “分到 B”是否真的“看到了 B”？ feature flag/参数化、默认值与回退、客户端/服务端一致性、assignment/delivery/exposure/trigger 的定义与日志契约 旧稿有配置下发；完整证据链与 ITT/触发口径待建
    6. 质量监控与故障诊断 实验何时应被阻断，而不是继续看效果？ SRM、A/A、漏斗计数、埋点缺失、跨组污染、延迟、护栏；按端/版本/时间定位；告警分级与处置 SRM 已有专篇；平台级健康看板和故障树待建
    7. 灰度、扩量与回滚 如何从空转到全量而不破坏比较？ dry-run/A/A → 小流量 → 扩量 → 固定观察 → 发布；变更记录、kill switch、自动护栏、阶段数据可比性 生命周期专题有部分内容；本目录缺“分流配置如何变化”的专篇
    8. Holdout 与长期基线 多次上线叠加后，长期净效果如何测？ 全局/业务域/功能簇 holdout；随机化单位、进入顺序、覆盖清单、冻结与轮换、污染、成本、长期效应解释 目前仅零散提及，优先补建
    9. 容量、权限与审计治理 平台规模化后谁能占流量、改配置、解释事故？ 实验注册、流量预算、冲突检测、审批、配置快照、owner、权限、SLA、复盘与清理 旧稿有模块清单，缺治理规则和资产台账
    10. 非标准流量机制 什么时候不能沿用固定比例用户级 A/B？ 分层/簇随机、switchback、网络干扰；MAB/CSR 与常规 A/B 的关系及推断约束 [[CSR-客户分群路由.md

    边界提醒：模块 10 是扩展层，不应挤占前九项基础设施的优先级；统计方法、MDE、指标定义、序贯停止的细节在[[Z_Project_DS/topics/实验设计与AB测试/index.md|实验设计与 A/B 测试]]其他专题，不在本目录重复写一套。

    三、几个最容易混淆的架构决策#

    1. “流量域”与“流量层”不是一个东西#

    • **域/namespace**首先回答“哪一类流量、哪些实验有资格使用这部分流量”，也可承担全局互斥与隔离。域不必机械等同业务部门：Search、Feed 是一种划分；全局保护域、特殊实验域也是可能的设计。跨域是否允许重叠，必须显式定义。
    • 层/layer**回答“同一域中哪些实验必须互斥、哪些可以并行”。常见做法是**同层共享有限桶并互斥，跨层独立分配而可重叠；但“分配正交”只减少人为分配相关，不保证处理之间没有真实交互。Google 的多层设计用于兼顾实验规模与参数冲突；Statsig 也把层作为互斥池并记录占量。Google 论文 · Statsig Layers
    • **实验/variant**分别回答“这部分桶归哪项实验”“实验内部给哪个版本”。两级分配应分开记录；预设比例不能在受众过滤与扩量后凭印象推断。

    一个示意：Search 域内“召回策略 A”和“召回策略 B”若修改同一链路，可放在同一互斥层；“召回策略”和“按钮样式”可在不同层并行，但若按钮改变了召回效果的呈现，仍需评估交互。跨层不是“自动因果独立”。

    2. Holdout 不是“再建一个普通实验层”#

    常规 A/B 比较**单项改动**；长期 holdout 把稳定随机的一批单元排除在指定的新功能/实验集合之外，用来估计**一组上线改动的累积净影响**。它是具体实验分配之前的横向约束；与受众筛选的先后顺序取决于平台实现，必须明确定义并记录覆盖哪些 feature、layer 或 domain。全局、业务域、功能簇 holdout 回答的是不同范围的问题。Statsig 文档明确区分 global 与 selected holdout，并要求随机化单位相容；LaunchDarkly 文档也将互斥层与 holdout 视为不同用途，但其“同一实验不能同时属于二者”是**该产品的限制**，不是通用定律。Statsig Holdouts · LaunchDarkly Holdouts · LaunchDarkly 互斥层

    设计前必须回答：基线版本究竟是什么？新功能是否都被纳入？holdout 用户是否会被其他实验污染？跨端/匿名身份能否保持稳定？保留多久、何时释放或轮换、用户机会成本是多少？长期 holdout 的结果是其覆盖集合相对被保留基线的效果，不能未经核对就解释为所有平台改动的总收益。

    3. 稳定分流与流量利用率存在张力#

    扩量、缩量、重分桶、实验结束回收桶都会改变谁处于什么版本。平台应优先明确“老用户是否保持原分组”“新增用户来自哪些桶”“缩量用户如何退出”“报告按哪个配置阶段分析”，而不是只提供一个可拖动的比例滑块。Statsig 的公开文档甚至指出，缩减 layer 占量可能使既有实验结果产生偏差，并说明了受众过滤在 layer 分桶之后执行时可能造成容量浪费。这些是**产品实现案例**，用于提醒我们在自有平台明确顺序与语义，而不是要求照搬。Statsig Layers

    四、建议的阅读与建设顺序#

    1. 可信底座：先完善对象/身份/受众、稳定分流、SRM/A/A、分配—曝光证据链。若这些不成立，更多 layer 只会放大不可信实验的数量。
    2. 规模化调度：再建立域/层/桶的统一词汇、冲突矩阵、容量管理和变更语义。用两个真实并行实验回放，而不是只画抽象架构图。
    3. 上线与长期验证：补齐灰度扩量、自动回滚及 holdout；先选业务域或功能簇的有界 holdout，再评估是否值得全局化。
    4. 扩展机制：在固定比例 A/B 稳定后，再整理 MAB、CSR、簇随机与 switchback 的准入条件和分析差异。

    每个专题后续按统一规格完善：它回答的问题 → 术语与边界 → 设计方案及权衡 → 一个可算/可跑的例子 → 质量检查与失败模式 → 平台字段/日志契约 → 一手来源 → 内部案例（若已核验）。当前阶段先定地图，不把缺失专题伪装成已有成熟文档。
